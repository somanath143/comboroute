# Backend roadmap for an SDE internship portfolio

The six reliability/performance/operations features discussed in chat are now implemented; see [implementation and operating instructions](BACKEND_FEATURES.md). The table below preserves the original design goals. Account lifecycle security in row 7 remains future work. The strongest story here is reliable multi-restaurant order orchestration backed by concurrency/recovery tests and measured query plans.

Existing strengths: server-authoritative integer pricing, deterministic route evaluation, cookie sessions, password hashing, role and ownership checks, MongoDB transactions, optimistic order transitions, payment signatures, idempotent checkouts, webhooks and regression tests.

| Priority | Addition | Concrete implementation | Evidence to show an interviewer |
|---|---|---|---|
| 1 | Durable payment reconciliation and refund jobs | Persist webhook deliveries in an inbox; a worker processes them with leases, retry limits, backoff and a dead-letter state. Schedule provider lookups for `captured`, `initialization_unknown`, `refund_unknown` and pending refunds. Use a transactional outbox for jobs created with order changes. Deduplicate operations by business ID, and reconcile external timeouts before resubmission. | Kill a worker after capture and before local completion, restart it, and demonstrate recovery with one order. Replay an event 20 times and prove one business effect. |
| 2 | Inventory and checkout reservations | Add stock counts and reservation documents with `reserved`, `committed`, `released` states. Atomically decrement available portions when checkout starts; freeze the bill/address/menu snapshot for a bounded payment window. An expiry worker releases reservations once, while payment races either commit or produce a tracked refund. | Run 50 concurrent checkouts for the last 5 portions; exactly 5 reserve successfully and stock never becomes negative. Test capture racing reservation expiry. |
| 3 | Observability and an immutable audit trail | Add structured logs with request/trace IDs, latency histograms and counters for payment mismatch/refund/quote failure. Record actor, action, resource, reason and timestamp for role changes, price changes, cancellations and refunds. Redact cookies, credentials, signatures and unnecessary personal data. | Follow one checkout through API, worker and webhook logs. Show a metric detecting a forced provider outage and audit evidence for an admin action. |
| 4 | Database performance and pagination | Replace full-catalog in-memory search/filtering with database queries. Introduce stable cursor pagination on `(createdAt, id)` for history and staff lists. Evaluate compound indexes for customer history and partner dispatch with `explain('executionStats')`. Cache public catalog responses with explicit invalidation after menu edits. | Seed 100,000 orders; publish query plans, documents examined, p50/p95 latency and cache hit rate before/after. Never cache a customer's response under a shared key. |
| 5 | Delivery assignment with concurrency controls | Add partner availability/capacity, assignment leases and expiry/reassignment. Use atomic claims with version checks and idempotent pickup commands. Verify role/assignment again when processing commands and reconnecting SSE streams. | Many partners race to claim one order: only one succeeds. A crashed partner's lease expires and assignment recovers without duplicate pickup. |
| 6 | API contracts and failure testing | Publish an OpenAPI spec with cookie authentication, validation errors, idempotency behavior and webhook schemas. Add reproducible local fixtures and CI checks for contracts, authorization, transaction races, worker restarts and provider faults. | A new developer can start the project and exercise the API without reading React. CI catches a deliberately broken ownership check. |
| 7 | Account lifecycle security | Implement email verification, hashed single-use password-reset tokens with expiry, session listing/revocation, and explicit session invalidation on sensitive account changes. Use a shared rate-limit store before scaling to multiple API instances. | Reset-token replay fails, expired/revoked sessions fail, and login throttling remains effective across two API instances. |

Suggested milestones:

1. **Reliability:** reconciliation worker + webhook inbox/outbox + fault-injection tests. This directly addresses the remaining manual payment recovery paths.
2. **Concurrency:** inventory reservations + assignment leases, with deterministic race tests and written invariants.
3. **Evidence:** API contract, observability and a load-test report. Finish this before starting another feature.

Useful primary references: [BullMQ retry/backoff](https://docs.bullmq.io/guide/retrying-failing-jobs), [MongoDB compound indexes](https://www.mongodb.com/docs/manual/core/index-compound/), [OpenAPI specification](https://spec.openapis.org/oas/latest.html), and [k6 API load testing](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/). A MongoDB-backed job worker can also be sufficient at this scale; adding Redis should have a clear purpose.

For the README and CV, publish actual measurements with machine specs, database size, concurrency, test duration and commit. A good eventual claim is “Designed idempotent order/payment workflows and demonstrated recovery from duplicate webhooks and worker crashes”; add performance numbers only after measuring them. Explain tradeoffs and remaining limits. Keep this as a modular monolith until you have a reason to introduce separate services.
